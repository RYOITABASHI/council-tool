# council-tool

> Status: **implemented, developer preview**. The core engine, MCP server, HTTP facade, and Android app described in [`PROTOCOL.md`](./PROTOCOL.md), [`PRODUCT.md`](./PRODUCT.md), and [`PLAN.md`](./PLAN.md) are built and in daily use; the specification documents remain the design record (v9.15).

A council of AIs — not models, **seats with context** — debating under a chair, with a human holding final approval.

## What this is

Most "AI council" tools (e.g. Karpathy's `llm-council`, `llm-roundtable`) mix several *models* and aggregate their answers through voting or merging. That diversifies model behavior, but every participant still sees the same prompt and the same context.

council-tool diversifies something else: **context**. A seat can be a web chat AI that has months of personal history with you, or a CLI coding agent that has read your actual repository — sitting at the same table, each bound by an explicit **context contract** that defines what it can see and what it's allowed to share.

Core design points:

- **Input and citation rules.** `SeatConfig.connection` is required and accepts `"cli"`, `"api"`, `"web"`, or `"local"`. It determines quota defaults and limits. Web-seat answers are submitted only through `transcribe_web_seat`. A connection change through `council.update_setup` is allowed only in `CREATED` and revalidates the entire setup, including quotas against the new connection limit. The meeting chair, when unaffiliated with a seat, and human participants, when unaffiliated with a seat, must explicitly request `view: "oversight"` and set `caller_seat_id` to `"chair"` when acting as chair or `"human"` when acting as a human participant. A convener has oversight read access through `get_state` and `get_packets` for meetings they convened. For `get_packets`, they specify `view: "oversight"` and `caller_seat_id: "convener"`. The core checks that the authenticated principal is the meeting’s convener. The input view, including when `view` is omitted, requires a `caller_seat_id` for an existing seat in the meeting that the authenticated caller holds or is authorized to drive. A chair using the input view supplies the `seat_id` of a seat they hold or are authorized to drive as `caller_seat_id`. The core rejects the reserved values `"chair"` and `"human"` in the input view. These values are reserved for `oversight` and chair-role operations. The core matches `"chair"` to the authenticated principal of the meeting’s chair and `"human"` to an authenticated human participant in that meeting. The chair is responsible for citing, reproducing, or mentioning only the current agenda in the synthesis text. The core checks the references declared in `cited_materials`. The core checks packet citation eligibility under PROTOCOL.md §6. Even when retrieving meeting-level packets, only the convener, chair, and human participants authorized to use `oversight` can retrieve superseded agendas, through that view. Seats without `oversight` authorization receive only the current agenda, including in meeting-level retrieval.

- **One core, adapters on top.** The engine (a "secretariat") runs the meeting state machine; surfaces (MCP server, mobile app, web app) are thin clients over it.
- **Seats, not models.** A seat is defined along three axes — *connection method* (web handoff / CLI / API / local), *usage condition* (subscription / API-billed / free), and *capability* (arbitrary labels like `long_context`, `fast_small`, used by the human or chair configuring the seat as a reference when choosing settings) — plus a **context contract** (role, shared materials, seat-specific materials, sharing policy, and the tool permissions the seat is granted). Frozen answers are the seats’ contributions to the meeting and are distributed within it regardless of `sharing_policy`. The secretariat and chair must keep seat-specific materials outside frozen answers out of round packets (`answer` and `critique`) distributed to other seats. This rule does not apply to citations in the synthesis. A `cite_in_synthesis` confirmation permits including the material in the synthesis and distributing that synthesis to all meeting participants. This is the authorized path for disclosing seat-specific materials within the meeting. Seats can use `share_with_confirmation` (the default), `share_freely`, `no_share`, or `{ kind: "share_with_seat", seat_ids: [...] }`. The object stores the set of destination seats in `seat_ids`. Each ID must refer to a seat in the resulting setup. The core checks this at stage (0) for `create_meeting` using only the request, and at stage (2) for `update_setup` using the stored current setup because existing seats omitted from the request remain in the resulting setup. Both operations return `invalid_argument` if any ID fails this check. Each meeting starts with integer `setup_version` 1. Every successful `council.update_setup` increments it by 1. For each meeting and `seat_id`, `delivery_epoch` increases monotonically and is never reused during the meeting. A new `seat_id` starts at 1. In v1, `update_setup` can add seats and update existing seats. If the update changes a seat’s `principal` or its set of `driver_principals`, the core advances that seat’s `delivery_epoch` and clears its delivery and ack records. All packets return to undelivered for that seat, prior acknowledgments are invalidated, and packets are delivered again to the newly authorized principals under the current setup and retrieval permissions. Each `council.get_state` and `council.get_packets` response is computed from a single consistent snapshot of meeting state. The returned `setup_version`, packet selection, and any `packet_state` values come from that same snapshot. An older packet set can never appear with a newer `setup_version` in one response. The `get_state` response includes each seat’s context contract. The `seats` array lists seats in the order of the current configuration array, and each entry contains its `seat_id`. Authorized drivers receive the seat input view for their assigned seats. Callers with neither a driver assignment nor another authorized meeting role receive `unauthorized`. For each entry, only the seat itself, its authorized drivers, the chair, and human participants receive that seat’s `seat_specific_materials` list, with each item’s `id` and the seat’s `sharing_policy`. The list and the integer `seat_specific_materials_count` are mutually exclusive. Callers without access to the list receive `seat_specific_materials_count` in the context contract. The contents are held outside the core. The core does not provide the contents of seat-specific material items directly in `get_state` or `get_packets` responses. The chair may cite those materials in the synthesis under the `cite_in_synthesis` confirmation rules above. The interface keeps materials together with the version from the response that contained them and updates the version used for confirmation only when it redisplays the materials. It passes that response’s `setup_version` to `council.confirm_share`. Only human principals participating in the meeting may call it: the human convener, the human chair, and humans registered through `human_participants`, an array of authenticated human principal identifiers supplied to `council.create_meeting` or `council.update_setup`. The core rejects calls from humans outside the meeting. The core rejects a version mismatch and records the version with the confirmation. A confirmation must match the material, purpose, destination when applicable, and the meeting’s current `setup_version`. A successful setup update invalidates earlier confirmations. For a `share_with_seat` confirmation, the core returns `not_found` at step (3) if the destination seat is absent from the current setup. If the seat exists and the `share_with_seat` policy excludes it from `seat_ids`, the core returns `invalid_state` at step (4) with detail `{ meeting_state, sharing_policy }`. The `no_share` policy prohibits use even if a confirmation exists, and the core rejects confirmation requests for those materials. The `share_with_confirmation` policy requires a matching record. The `share_freely` policy permits citation and sharing without a confirmation. The chair must declare each seat-specific material and packet relied on in the synthesis in `cited_materials`, using `packet:` references for packets. The core checks `sharing_policy` only for `seat:` references. The chair may cite frozen received versions of `answer` and `critique` packets, as well as the current `agenda` and `gate_decision` packets, via `packet:` without sharing confirmation. Flash packets, superseded agendas, superseded answer or critique versions, and unverified versions are ineligible for citation under PROTOCOL.md §6. If a flash contains an important point, the chair states it in their own words in the synthesis without citing the flash. At stage (3), the core resolves the declared material and packet references and returns `not_found` for any missing reference before proceeding to stage (4). At stage (4), any ineligible material or packet reference in `cited_materials` causes the core to reject the entire synthesis with `invalid_state` and `detail: { meeting_state, offending_materials }`. The `offending_materials` field is an array of original `material_ref` strings. Each offending reference appears once, in order of first occurrence in `cited_materials`. If the meeting state is also ineligible, `detail` includes all applicable stage (4) facts. In v1, humans share materials outside the meeting manually and record any required confirmation beforehand using `confirm_share` with `share_external`. The v1 core has no operation that delivers seat-specific materials directly to another seat. The `share_with_seat` policy permits only sharing with seats in its destination set. It allows neither synthesis citations nor external sharing. Humans record `share_with_seat` before delivering the material to the target seat outside the core. Any future seat-to-seat delivery operation must check for a confirmation matching the material, purpose, destination, and current setup version before delivery and reject the operation if none matches.
- **A real meeting protocol.** `council.create_meeting` requires `chair`. When no chair is selected, the calling interface or agent supplies the convening agent as `chair`. Meeting creation saves an agenda packet with the topic and shared-material references. All participants can retrieve it. While the meeting is `CREATED`, the convener or chair can use `council.update_setup` to update the `chair`, registered `human_participants`, seats, context contracts, shared materials, and round settings, including settings inherited through reopen. The operation merges plain objects field by field, including each round entry in `round_settings`, and preserves omitted fields. Scalars, tagged unions, and arrays are replaced as whole values. The `seats` array is an exception: entries match by `seat_id`, and omitted seats remain registered. When the update lists every existing seat, the supplied array determines the order, including any new seats. When it omits any existing seat, existing seats keep their positions and new seats are appended in the order supplied. To clear a value, pass `null` explicitly for a field whose creation type includes `null`. A change to shared materials creates a new agenda packet linked via `supersedes`. The seat input view delivers only the current agenda. The oversight view returns all agenda versions with their `packet_state`. Only materials from the current setup can be confirmed. A replaced agenda is for reference only and cannot serve as the basis for confirmation. It has `version: "superseded"` and retains `not_applicable` for both `verification` and `reception`. The chair starts R0 with `open_round`, which freezes the setup. The core rejects the R0 call unless the meeting has a human convener, a human chair, or a registered human in `human_participants`. The core rejects subsequent setup updates. R0 independent answers (seats can't see each other yet) → R1 mutual critique → a chair gate that decides whether a scoped R2 is needed. Every claim must state the condition under which it would reverse. Submissions that omit required answer elements are still accepted. No anonymization — session sizes are small enough that writing style gives people away anyway, so independence is protected by keeping R0 private instead.
- **Barrier-synchronized rounds, delta catch-up.** Rounds advance only when every required seat has resolved to received / absent / waived. Late seats catch up via diffs, not full re-sends. A separate "flash" lane carries early, explicitly-provisional takes without blocking or polluting the formal record.
- **Seat drivers.** When `caller_seat_id` identifies a seat, the authenticated caller must match that seat’s `principal` or be listed in its `driver_principals`. Authorized drivers have the seat’s permissions, including fetching and acknowledging its input via `get_packets`, submitting non-Web answers, and submitting flashes for a designated flash seat. Returning a packet to either the seat principal or an authorized driver marks it as delivered to that seat. Either can acknowledge it for the seat. Unacknowledged packets remain eligible for redelivery. Drivers can use oversight under an independently held convener, chair, or human participant role, subject to that role’s access rules.
- **Submission limits.** Each seat has an accepted-submission limit per meeting. Web (manual handoff) seats default to 4 with a maximum of 6. CLI, API, and local seats default to 10 with a maximum of 20. Set the optional integer `SeatConfig.quota` via `create_meeting` or `council.update_setup`. Both operations reject non-integers and values outside 1 through the connection method’s maximum. The core sets the quota from the explicit `SeatConfig.quota` value or, for a newly registered seat with no quota specified, the connection method’s default. The core does not derive quotas from capability labels. The core charges one unit to the seat each time it accepts a `submit_answer`, seat `submit_flash`, or `transcribe_web_seat` submission, including each replacement, and rejects submissions above the limit. Under the [common validation order](./PROTOCOL.md#共通検査順), exceeding the limit returns `invalid_state` at stage (4) with `quota_exceeded: true` in `detail`. If the round is also frozen, `detail` includes both `round_frozen: true` and `quota_exceeded: true`. `get_quota` is an advisory preflight check.
- **In-meeting instructions.** Human participants and the chair can use `council.post_message` with a `{ text }` body. Posting is allowed in `CREATED`, `OPEN`, `GATE(round)`, `SYNTHESIZING`, and `AWAITING_APPROVAL`. After the R0 barrier, `GATE(R0)` waits for the chair to open R1. After the R1 barrier, `GATE(R1)` waits for the chair’s gate decision. The core accepts `council.chair_gate` only in `GATE(R1)`. It records the decision and transitions in the same operation, to `SYNTHESIZING` on Pass or `OPEN(R2)` on Fail. It rejects repeat calls because the meeting has left `GATE(R1)`. R2 is limited to the issues specified in that decision, and its barrier leads directly to `SYNTHESIZING`. The core rejects posts in `APPROVED` and `REJECTED`. After reopen, posts go to the new meeting. Participants retrieve the resulting `note` via `get_packets` as a meeting-level packet (`round: null`). During an open round, the core holds notes from authors with pre-barrier access to other seats’ answers, including eligible chairs and humans using oversight, from seat delivery until that round’s barrier, using the same mechanism as flashes. Each held note is associated with the round in which it was posted. Until that round’s barrier completes, the same oversight access restrictions apply as for its pre-barrier answers. Oversight withholds the note from conveners, chairs, and human participants who are seat principals or authorized seat drivers. After the barrier, all meeting participants can retrieve it as a regular meeting-level packet. Before the barrier, note authors must avoid quoting or summarizing other seats’ answers from that round. The sharing rules prohibit including seat-specific materials outside frozen answers in notes and flashes. This lightweight channel is limited to instructions and clarifications for the chair.
- **Deadlines, quorum, and the `waived` state.** Absent seats are tracked by count ("received 1/2, waived 1" is always spelled out in the synthesis, never just "done"). The core accepts `council.waive_seat` only for a `pending` or `transcribed_pending_attest` seat in the current `OPEN` round. It rejects calls for received seats or seats in frozen rounds. A waiver applies only to that round. The core processes all state-changing operations, including submissions, waivers, absence declarations, and chair actions, in the order it receives them. The core serializes registration and takes each operation’s receipt time from its single monotonic clock for ordering and determining deadline eligibility for initial submissions and transcriptions. State changes take effect at processing time. A round’s internal start time is the monotonic clock reading at the opening operation’s position in the total order. It anchors relative deadlines and the meeting timeout for that round’s `OPEN` period. The API response field `opened_at` returns the wall-clock value retained when the start time was recorded. Each sweep is ordered by its scheduled time. The core registers its timer entry only after confirming that the clock is strictly past the scheduled time. Every operation registered after that entry has a receipt time strictly later than the scheduled time. An operation received strictly after a sweep’s scheduled time T waits for that sweep to run, even if the operation arrives before the timer entry is registered. At any given time, the core processes operations received at or before that time ahead of all sweeps scheduled for that time. At the same time, round deadline sweeps run in creation order before meeting-timeout evaluations, including evaluations already queued. Initial submissions and transcriptions received at or before the deadline are deadline-eligible, even when processed after the deadline. Replacements of current or invalidated versions inherit the initial version’s deadline eligibility regardless of connection type. The core checks round and seat state at the operation’s position in the total order. A valid waiver processed before a round deadline sweep in the total order leaves the seat in `waived` and outside that sweep. The core rejects a later waiver for a seat the sweep marked absent. Set round deadlines and quorums through `round_settings: { R0?: { deadline?, quorum? }, R1?: { deadline?, quorum? }, R2?: { deadline?, quorum? } }` in `create_meeting` or `council.update_setup`. A deadline is either `{ kind: "absolute", at: ISO 8601 timestamp }` or `{ kind: "relative", seconds: positive integer }`. In saved round settings, `deadline: null` leaves the deadline unset. Seats are required by default. Only seats configured with `optional: true` are optional. They do not block the barrier, and their received answers are distributed under the same rules as required-seat answers. The barrier freezes as soon as all required seats reach a terminal receipt state (`received`, `absent`, or `waived`), regardless of whether a deadline exists or has passed or whether quorum is met. At freeze, the core computes and records `quorum_met` in the reception tally using only required seats in `received`. The deadline sweep is one way to move seats to a terminal state. If there is no round deadline and a required seat remains unresolved, the meeting waits. The chair can waive the seat or call `council.declare_absent`. Once accepted, these operations set the seat to `waived` or `absent` respectively, regardless of the current version’s verification state. The version retains its attestation state in the packet record. Only the chair principal can declare a seat absent, and only if the target round is `OPEN` and the seat is `pending` or `transcribed_pending_attest`. The core moves the seat to `absent` and records the reason using the seat’s submission history for that round. If an attestation mismatch invalidated any version in that round, the reason is `attest_mismatch`, including when the deadline sweep or a chair declaration marks the seat absent. Otherwise a chair declaration records `chair_declared`, and the deadline sweep uses `deadline_no_submission` only for a seat with no answer or critique submission that round, including Web-seat transcriptions. Flash and note packets do not count as submissions for absence reasons. A flash-only seat marked absent by the deadline sweep receives `deadline_no_submission`. The core rejects calls for seats already `received`, `waived`, or `absent`. At the barrier, the synthesis reception summary records optional seats still in `pending` as `absent` (see PROTOCOL.md §6 for absence reasons) and optional seats in `transcribed_pending_attest` as “attestation unconfirmed.” The core excludes unconfirmed answer content from received-answer delivery and synthesis. The barrier snapshot is final. A deadline sweep acts only if its target round is still `OPEN` at the sweep’s processing position in the total order. The barrier freeze invalidates that round’s sweep, and any later sweep has no effect. Once the barrier freezes, the round is closed and the core rejects further `submit_attest` calls for it. At freeze, the oversight view reports `packet_state.reception: transcribed_pending_attest` only for a valid current transcription with an unresolved attestation. A version superseded while its attestation was unresolved has `packet_state.reception: superseded`. The same version distinction applies to `unverified_items.state` under PROTOCOL.md §6. There, “attestation unconfirmed” is a display label. At freeze, the API returns the combination of `verification: unverified` and `reception: transcribed_pending_attest` only for a valid current transcription with an unresolved attestation. The optional round-specific `quorum` takes precedence over the top-level `quorum`, which supplies the default for each round. Meeting creation and setup updates validate both forms and accept only integer quorum values from 1 through the seat count. The core validates the entire resulting configuration on `council.update_setup`. If a change leaves a saved value invalid, such as a quorum above the new seat count, the core rejects the whole update without applying any changes. Supply the corrected settings in the same call. `council.open_round` does not accept `quorum` for any round. Every round uses the same deadline precedence. A deadline supplied when opening the round takes priority, followed by the saved setting for that round, then any relative duration resolved for the immediately preceding round, re-anchored to the current round’s start. Otherwise the round has no deadline. Only relative durations carry over between rounds. R2 follows the same rule, with the Fail decision’s `r2_deadline` as the opening override and R1 as the preceding round.
- **Meeting timeout.** Set `meeting_timeout` in `create_meeting` or `council.update_setup` as a positive integer in seconds. It defaults to 259200 seconds (72 hours). The core rejects zero, negative values, and non-integers. The specification sets no upper bound. At any given time, the core first processes operations received by that time, then runs the round deadline sweep, then processes the meeting timeout evaluation. Each evaluation belongs to the specific open round or applicable wait for the chair for which it was scheduled. If that period has already ended at the evaluation’s position in the total order, the core skips the item. If the period is still current, the core compares the item’s scheduled time (logical time) with the start of that period plus `meeting_timeout`. The core sets `timeout_exceeded` and exposes it through its state API, including via MCP `get_state`. Surfaces use the same flag for display and notification, including the system message in the meeting thread. Seat receipt states and submission eligibility are unaffected.
- **Transcript integrity and attestation.** On acceptance, the core assigns each packet a unique UUID as its `packet_id`. Identical submissions are accepted as distinct packets without deduplication. Delivery, acknowledgments (`ack_packet_ids`), and packet references use `packet_id`. Seat input responses include the seat’s current `delivery_epoch`. An acknowledgment is eligible for acceptance only if it carries the current value from the delivery response. The core ignores and audits acknowledgments whose epoch differs from the seat’s current epoch, whether older or newer, and continues retrieving packets. The `packet_sha` hash checks content equality and integrity against a hash obtained through a trusted channel. Its calculation excludes `packet_id` and `seq`. Authenticated principals identify the parties, and attestations confirm the transcribed content. Web-seat answers enter only through `transcribe_web_seat` and are **unverified by default** until attested — the meeting convener, the authenticated principal bound to the target Web seat, or an authorized driver for that seat can confirm the verbatim text. In successor versions, these callers can use `hash_match` to submit a source hash for the core to verify. Only the meeting convener principal, the authenticated principal bound to the target seat, or an authorized driver for that seat can call `transcribe_web_seat`. The core rejects calls from other participants. Caller authorization for `submit_answer` and `transcribe_web_seat` applies regardless of connection type. At stage (4), the core rejects `submit_answer` for Web seats and `transcribe_web_seat` for non-Web seats with `invalid_state`, using the standard detail keys and deadline eligibility rules. The deadline sweep leaves timely transcriptions in `transcribed_pending_attest` while attestation is unresolved. A confirmed attestation moves the seat to `received` only while the round is open and the target seat is in `transcribed_pending_attest`. A mismatch confirmed before the sweep returns the seat to `pending`. A retranscription that replaces the invalidated version inherits the initial version’s deadline eligibility and is subject to the seat and round state at processing time. An attestation mismatch confirmed after the sweep makes the seat `absent` immediately. The core then rejects retranscription. Retranscription rejection explanations report the seat and round state at processing time separately from deadline eligibility. The convener is always an attest recipient regardless of eligibility to receive the target transcription and reads attest packets through oversight subject to round authorization. The core stores the input values directly in a fixed attest packet body. The body contains `{ method, result }` for `verbatim_confirm` and `{ method, result, source_hash }` for the successor version’s `hash_match`. The `source_hash` field is required for `hash_match` and forbidden for `verbatim_confirm`. Extra fields return `invalid_argument` at stage (0). The v1 core accepts only `verbatim_confirm`. A `submit_attest` call with `method=hash_match` returns `invalid_argument` at stage (0) because the method is outside the allowed values for v1. The `hash_match` verification rules in PROTOCOL.md §4.3 are specified for a later version. This exists because we've seen a handoff get silently altered in transit; "trust the paste" was not good enough.
- **The chair is a role, not a model.** In v1, the chair may be a seat, a human, or an agent principal without a seat. `ChairConfig` requires `principal`, the authenticated principal’s string identifier, and accepts optional `display_name` (`string | null`) and `seat_id` (`string`). A convening agent without a seat omits `seat_id` and sets `principal` to its own identifier. A chair or other participant with oversight access is treated as holding each seat for which they are the seat principal or an authorized driver. Authorization is evaluated per principal and role in the round. The same pre-barrier oversight restrictions on other seats’ current-round answers apply for each seat the participant holds or can represent. The optional `seat_id` is for display and consistency. If set, it must identify a seat bound to the chair’s principal in the resulting configuration, or `create_meeting` and `update_setup` reject the request. The chair's synthesis output must always carry four sections: agreements, minority opinions, unverified items, reversal conditions. Only answers finalized at a barrier can support agreements. The synthesis records unverified answer references in `unverified_items`. Each oversight entry is `{ packet, packet_state, missing_records, declared_missing_records }`. The `missing_records` string array contains core-detected omissions only for a frozen received structured submission version and is empty otherwise or when no omissions apply. The oversight view returns accepted chair reports for the same packet version in `declared_missing_records`, with an empty array when there are none. The field names identify the source. The chair submits omissions in prose-only answers as `{ seat_id, packet_id, note }` entries in the synthesis input array `missing_records`. The core saves a chair-supplied prose omission only if the `packet_id` identifies the frozen received version for that seat in its round and the core verifies that the version is a prose-only submission with no structured fields. It discards and logs records that fail either check. For structured submissions, the core uses its own mechanically detected omissions from the frozen received version. Final approval is always a human action.
- **No silence.** A seat qualifies for the flash lane only when `SeatConfig.flash` is explicitly set to `true`. Capability labels never assign seats to the flash lane automatically. Set this optional boolean through `create_meeting` or `council.update_setup`. It defaults to `false`. The chair can submit interim observations separately under the chair role (`seat_id: "chair"`). Participant flashes are available immediately. Flashes submitted during an open round by a principal authorized to read other seats’ answers for that round are held back from participants until the barrier. Before the barrier, flash authors must avoid quoting or summarizing other seats’ answers from that round. High-cost seats are never burned just to fill dead air.

The chair supplies `agreements`, `minority_opinions`, unverified answer references as `{ seat_id, packet_id }` entries in `unverified_items`, prose omission reports in `missing_records`, `reversal_conditions`, `recommendation`, and `cited_materials` in the synthesis `body`. Both input arrays, `unverified_items` and `missing_records`, are optional. Omitting either has the same meaning as supplying an empty array for that field (no declarations). If either field is supplied with a non-array value, including null or an object, the core rejects the entire `synthesize` call with a call-level type error. The core discards invalid entries individually only in `unverified_items` and `missing_records` when supplied as arrays. It records those entries in the audit log and continues processing the synthesis. Any defect in `cited_materials` causes the core to reject the entire synthesis under the citation rules in PROTOCOL.md §6. For each `unverified_items` entry, the core checks that its `packet_id` identifies a packet from the same meeting and seat, using the linked submission version for core-generated omissions. The core saves a chair-supplied unverified answer reference only when the referenced version has kind `answer` or `critique` and `packet_state.verification` is `unverified`, including pending and mismatched attestations. Only the meeting’s convener, chair, and human participants can retrieve superseded versions in the oversight view, subject to the same round authorization conditions. The core discards and records in the audit log any unresolved entry or ineligible reference, including references to verified answers or `flash` packets. Every saved `unverified_items` entry is an object with `seat_id`, `packet_id`, `state`, and `source` fields. There are no string-only entries. The core sets `source` to `"chair"` for chair-supplied unverified answer references and `"core"` for core-generated omissions. Core-generated omissions retain the seat and `packet_id` of the version in which they were detected. The core saves one omission entry per affected version and stores the missing structured-submission field names in its `missing` string array, using each name exactly as defined in the schema. Each name appears once per version. v1 records omissions at field level. For example, an empty `claims` array yields `missing: ["claims"]`. A claim missing both fields yields `missing: ["statement", "reversal_condition"]`. Chair-supplied entries omit `missing`. The `note` in `declared_missing_records` holds the chair’s description of the omission. The core ignores any input `state` and supplies the saved value from its reception records. The synthesis retains accepted prose omission reports as `{ seat_id, packet_id, note }` entries in `declared_missing_records`. A submission with any structured field counts as structured, including one with an empty `claims` array. The prose-only path applies only to submissions without structured fields. The core detects an omission when `claims` is empty or either claim field (`statement` or `reversal_condition`) is omitted, null, or a whitespace-only string, including the empty string (see PROTOCOL.md §§3.2–3.3). The core ties each structured omission to the submission version where it was detected. It saves structured omissions only for frozen received versions and marks their entries in `unverified_items` as core-generated. The oversight view returns an empty `missing_records` array for all other versions, including superseded versions. The chair is responsible for reviewing prose-only answers during synthesis. Omissions the chair leaves undeclared go unrecorded. An empty `unverified_items` array means there are no recorded unverified items. Undeclared omissions in prose may still exist. The interface displays an empty `unverified_items` array as “No records” (「記録なし」). It may display an empty `agreements`, `minority_opinions`, or `reversal_conditions` array as “None” (「なし」) or equivalent, field by field. The core computes `reception_summary` from the reception table, replacing any caller-supplied summary.

Only human participants, as defined for `council.confirm_share`, may call `council.approve` to approve, reject, or reopen. The core rejects calls from humans outside the meeting and calls after the meeting leaves `AWAITING_APPROVAL`. The state transition gives the decision effect only once. A `council.approve` call with `decision: "reopen"` requires a nonempty `reopen_points` array of strings. The core rejects a missing or empty array. Use the selected strings from the final gate decision’s `unresolved_points` as-is, the text of selected opinions from the synthesis’s `minority_opinions`, and any free-form input as entered. The new meeting’s `agenda.topic` joins the strings in array order with ` / `. The human caller of `council.approve` who executes reopen becomes the new meeting’s convener. The new meeting inherits the original meeting’s chair and `human_participants` by default. It inherits each seat’s configured quota and the configured values of `round_settings`, top-level `quorum`, and `meeting_timeout` without carrying over evaluated times. For R0, R1, and R2, the core uses saved absolute deadlines from `create_meeting`, `council.update_setup`, or reopen inheritance only if they are in the future when the round starts. Otherwise the core records and skips the deadline and applies the next rule. If no rule yields a deadline, the round proceeds without one and the meeting timeout still applies. A past absolute time is accepted when saving settings. The core rejects a call when an absolute deadline passed as an override (`deadline` in `council.open_round` or `r2_deadline` in `chair_gate`) is already in the past at the monotonic clock reading when the core processes that operation at its position in the total order. The core converts absolute deadlines to monotonic clock values at round start for saved settings and at processing time for overrides. The core derives the offset from wall-clock and monotonic clock readings taken together in the conversion step. Once converted, the monotonic deadline is fixed and is never recalculated. The core preserves the full fractional precision of ISO 8601 inputs and uses only monotonic clock values for time comparisons, with no rounding or truncation during conversion or comparison. It retains the original ISO 8601 values for display. The saved-setting skip rule does not apply to overrides. The convener or chair can change the inherited settings through `council.update_setup` while the meeting is `CREATED`.

Seat IDs and seat-specific material item IDs must match `[A-Za-z0-9_-]+`. The core rejects IDs containing `:` during `create_meeting` and `update_setup`, so `packet:<packet_id>` and `seat:<seat_id>:<item_id>` can be parsed unambiguously. Seat IDs must be unique within a meeting. Both operations reject duplicate `seat_id` values in the `seats` array and reject the reserved values `"chair"` and `"human"` as seat IDs.

## Why not just fork llm-roundtable?

`llm-roundtable` (MIT) is a useful reference for CLI-seat driver mechanics, and is credited as such. But its design center is different: anonymized models, vote-based aggregation, no chair. council-tool is the opposite shape: named seats, context contracts, an explicit chair, and mandatory human approval. We're not forking it.

## Surfaces (priority order)

1. **MCP server** — the primary interface for now. In v1, CLI seats primarily use a driver in the secretariat host’s adapter layer, which launches the CLI, passes the prompt, and submits the output on the seat’s behalf. Independently running agents can also participate directly as MCP clients.
2. **Mobile app** (Expo / React Native, Android-first) — a group-chat-style UI modeled on LINE's interaction patterns (not its assets or trademarks): a session list doubles as a chat list, a meeting thread as a chat room, receipt state as read receipts, the synthesis as a pinned note. Seat execution stays server-side; the app is a thin client.
3. **Web app** — deferred. Browser automation for web seats is frozen as an out-of-scope safety norm, not just a v1 limitation; web seats are handed off manually, by design, not scraped.

You can run this with zero API spend: subscription-based CLI/web seats plus a local model are enough to hold a meeting.

## Status

Implemented: the core meeting engine and store, the MCP server, the HTTP facade with its host runner (CLI seats, interruption reconciliation, execution bounds), the Fold hosting scripts under `scripts/fold/`, and the Expo Android app under `app/`. The engine test suite runs in two store modes (linked and link-free) and the full meeting flow — create, rounds, synthesis, human approval, and resume after a mid-run kill — is verified end-to-end on a single Android device. See `PLAN.md` for the phase breakdown and `PROTOCOL.md` / `PRODUCT.md` for the specification.

## Your accounts, your CLIs

council-tool is bring-your-own-subscription. It drives the official Codex and Claude Code CLIs that **you** install, unmodified, on your own machine, signed in with **your own** account through each CLI's own login flow. The app and backend never see, store, or transmit your credentials, embed no API keys, bundle neither vendor's binary, and proxy nothing through any server of ours — a seat invocation is a local process spawn of the CLI, the same binary you would run in a terminal.
